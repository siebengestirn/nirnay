# M3.5.1 — typed durable execution events — 2026-11-21

Dated evidence for per-fill execution records. Synthetic fills only; no
provider data, broker endpoint or live order.

## Defect

`OmsStore` retained only cumulative `filled_quantity` and `filled_notional`.
Those aggregates cannot faithfully represent corrections, busts, multiple
partial fills, event ordering or differing charge provenance. `apply_fill`
recorded only opaque event keys, not a typed execution record.

## Correction

- Added `FillEvent` with schema version, stable execution id, broker event id,
  OMS/client order id, side, quantity, price, currency, broker and receive
  timestamps, source, account scope, charges, `ChargeStatus`
  (`Estimated`/`BrokerConfirmed`) and provenance.
- `OmsState` now persists a `BTreeMap<execution_id, FillEvent>`, so every fill
  is a durable, independently identifiable journal record.
- `apply_typed_fill(FillEvent)` is the typed entrypoint. `apply_fill` remains a
  thin wrapper for simulated reports and explicitly records estimated charges
  and paper provenance; it cannot assert broker-confirmed values.
- Duplicate execution ids and broker event ids are idempotently ignored; the
  already-persisted event is not replaced. This is idempotent drop, not a
  content-conflict error. Unsupported schema versions and missing ids fail
  closed.

## Tests

Four new tests cover: per-fill typed persistence and field retention, duplicate
idempotence, survival across restart, and rejection of an unsupported schema.
26 `authoritative-oms` tests pass in total (22 prior + 4 new), plus full
`make check`.

## Boundary

This milestone makes executions durable and identifiable. It does not project
them into the account journal, does not claim exactly-once broker delivery and
does not establish accounting correctness. Account projection and reconciliation
are separate milestones.
